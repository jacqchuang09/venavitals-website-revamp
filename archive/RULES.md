# Rules — how the agent works

You are trusted to move this project forward with judgment, taste, and creativity. These are not a checklist to satisfy — they are the few things that keep the work coherent and honest. **Within them, innovate freely.**

## Get oriented, then build

- Skim the docs so you know the goal and audience (`MASTER_PLAN`), the look (`DESIGN_GUIDELINES`), the journeys (`USER_JOURNEYS`), and the approved copy + media (`CONTENT`, `ASSETS`). `TASKS` is the running guide.
- Then make real progress. Pick up the next meaningful work — reorder, combine, split, or add tasks when a better path is obvious. You don't have to stop after one thing; batch related work and keep momentum.
- **Take initiative.** If you see a better structure, component, interaction, animation, or page, build it or prototype it. Propose bold ideas. A surprising, excellent result is the goal — not minimal compliance.

## The few things to hold firm

- **Honesty — this is a medical product.** Don't invent or overstate facts, numbers, names, quotes, or claims. For anything that makes a claim, use the approved copy in `CONTENT.md` and respect its `VERIFY` / `GAP` notes and the lines we hold in `MASTER_PLAN.md` (never imply FDA-cleared / approved / for sale; no outcome claims; "comparable to the arterial line" only with the citation). Non-claim microcopy, headings, structure, and UX are yours to improve freely.
- **Accessibility & quality.** Keep it readable and usable, and test what you build before calling it done.
- **Hard-to-undo moves.** If something is destructive or reshapes the whole project, give the user a quick heads-up first. Everything else, just proceed.

## Design & tech: wide latitude

- `DESIGN_GUIDELINES.md` is a foundation to build on and extend, not a cage. Make strong choices, invent new patterns, add tokens, push the craft.
- Choose the tools and libraries that serve the work. If you change the stack from `IMPLEMENTATION_PLAN.md`, just note why in `DECISIONS.md` so the team isn't surprised.
- Reuse components where it helps; rebuild when you can do better.

## Keep the project's memory

As things change, update the docs so they stay true (`TASKS`, `CONTENT`, `DECISIONS`, `LEARNINGS`, `CHANGELOG`). When something teaches you a lesson, fold it back into the docs so the project gets smarter over time. A lesson that doesn't change a doc isn't learned.

## When you finish

Tell the user briefly **what you did and how to test it**, then keep going or hand back. That's it.
