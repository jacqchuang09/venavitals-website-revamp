# Rules — how the agent works

The agent is trusted to move the project forward with judgment, taste, and creativity. These are not a checklist to satisfy — they are the few things that keep the work coherent and honest. **Within them, innovate freely.** They are also living: when a rule proves wrong, improve it.

## Get oriented, then build

- Skim the docs so you know the goal and audience (`MASTER_PLAN`), the look (`DESIGN_GUIDELINES`), the journeys (`USER_JOURNEYS`), and any approved copy/media (`CONTENT`, `ASSETS` if present). `TASKS` is the running guide.
- Then make real progress. Pick up the next meaningful work — reorder, combine, split, or add tasks when a better path is obvious. Don't stop after one thing; batch related work and keep momentum.
- **Take initiative.** If you see a better structure, component, interaction, or flow, build it or prototype it. Propose bold ideas. A surprising, excellent result is the goal — not minimal compliance.

## The few things to hold firm

- **Honesty.** Follow the lines we hold in `MASTER_PLAN.md`. Don't invent or overstate facts, numbers, names, quotes, or claims; if a claim isn't backed, leave it out and say so. Where approved copy exists, use it for anything that makes a claim.
- **Accessibility & quality.** Keep it readable and usable, and test what you build before calling it done.
- **Hard-to-undo moves.** If something is destructive or reshapes the whole project, give the user a quick heads-up first. Everything else, just proceed.

## Design & tech: wide latitude

- `DESIGN_GUIDELINES.md` is a foundation to build on and extend, not a cage. Make strong choices, invent new patterns, add tokens, push the craft.
- Choose the tools and libraries that serve the work. If you change the stack from `IMPLEMENTATION_PLAN.md`, note why in `DECISIONS.md` so the team isn't surprised.
- Reuse components where it helps; rebuild when you can do better.

## Keep the project's memory (the improve loop)

As things change, update the docs so they stay true (`TASKS`, `DECISIONS`, `LEARNINGS`, `CHANGELOG`, and any content docs). When something teaches you a lesson, fold it back into the docs and `RULES.md` so the project gets smarter over time. A lesson that doesn't change a doc isn't learned. Every few sessions (or when asked), run a quick retro from `LEARNINGS.md`.

## When you finish

Tell the user briefly **what you did and how to test it**, then keep going or hand back.
